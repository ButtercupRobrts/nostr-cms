<context>
Verified divergences (the "why"):

1. **Editor video bug (MEDIA-PIPE-02)** — `AdminNotes.tsx:613` and `AdminBlog.tsx:301` call `stripImageMetadata(file)` unconditionally on every file. For video/*, `loadImage()` rejects (`mediaProcessing.ts:60` 'Failed to load image') → outer catch → "Upload Failed". handleDrop/handlePaste explicitly accept video/* then the loop kills it. Repro: drop any video on the New Note textarea.
2. **iOS crash path** — editors upload videos via `BlossomUploader` → `file.arrayBuffer()` → memory spike that crashes iOS Safari on large files. Dialog/AdminMedia deliberately use `streamUpload` for video (chunked hashing + streaming PUT).
3. **Single-server** — editors upload to `blossomRelays[0]` only; picker uploads fan out across all selected relays via `Promise.any`.
4. **Error unwrap** — `BlossomUploader` throws `AggregateError` (Promise.any); editors show `err.message` = useless noise. Dialog/AdminMedia unwrap inner messages (`MediaSelectorDialog.tsx:257-259`).
5. **useUploadFile** (`src/hooks/useUploadFile.ts`) — no metadata stripping at all (profile pics/DM attachments keep EXIF/GPS); also BlossomUploader-for-videos. Separate shape (mutation hook) — stretch task.

Verified shared pieces (checked against nostrify source, not assumed):
- `streamUpload(file, servers|string[], signer, expiresIn=15min)` → `tags[][]` with `['x', sha]` and `['url', ...]` tags.
- `BlossomUploader` (`node_modules/@nostrify/nostrify/dist/uploaders/BlossomUploader.js`): `upload()` does `await file.arrayBuffer()` for the digest — **the iOS memory hazard is structural fact**, not just convention. `Promise.any(servers.map(PUT /upload))` fires ALL server uploads concurrently, resolves on first success — the "fan-out" is real. Returns tags `[['url',...],['x',sha],['ox',sha],['size',...],['m',type]]`.
- **`expiresIn` drift**: BlossomUploader default is 60_000 (1 min). AdminMedia passes `15*60_000` explicitly; the dialog passes nothing → its image auth tokens are 1-min today. Helper unifies at 15 min — deliberate, harmless normalization (token only needs to outlive the PUT).
- **Signer type (CORRECTION)**: `BlossomUploader` requires `NostrSigner` (`@nostrify/types`: getPublicKey + signEvent + nip04/nip44); `streamUpload` accepts loose `{signEvent:(unknown)=>Promise<unknown>}`. Helper MUST declare `signer: NostrSigner` — the loose shape would fail typecheck at the BlossomUploader call (missing getPublicKey etc.). Also tighten `streamUpload`'s own param to `NostrSigner` (it only calls signEvent; NostrSigner→loose-param assignability holds via method bivariance, but correct types propagate the constraint).
- `stripImageMetadata(file)` → `{file, stripped, reason?: 'gif'|'canvas-failed'}`; caller must warn on 'gif' (AdminNotes:615-620 toast wording is the convention). `loadImage` rejects on non-images — never call on video.
- `mediaProcessing.ts` does NOT currently import BlossomUploader — add `import { BlossomUploader } from '@nostrify/nostrify/uploaders'` and `import type { NostrSigner } from '@nostrify/types'` (verify exact import path compiles; nostrify re-exports types from the package root too).
- Post-upload differs per callsite and stays there: dialog invalidates `blossom-blobs` + switches to browse; AdminMedia feeds pendingVideo; editors insert URL at cursor (AdminNotes `content`/`setContent`, AdminBlog `formData.content`/`setFormData`).

**REST vs websockets audit (bitkarrot's "don't force the relay to change" prerogative):**
- Upload transports hit `PUT {blossom-server}/upload` + `GET /list/` — BUD-standard Blossom protocol endpoints, not swarm-custom REST. Same boundary the open upstream blossom-media PRs already live on; media upload has no nostr-WS alternative. **Zero new REST surface, zero relay changes required.**
- `streamProcessVideo`/`processVideo` (swarm ffmpeg extension — the one non-BUD endpoint) is NOT touched; stays inside AdminMedia's optional flow as a pre-existing upstream question.
- Site config/blossom-relay discovery is kind-30078 over relay WS — nostr-native.
